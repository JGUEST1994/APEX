Tests last run: 2026-11-19, `ruff check` clean, **286 passed**, with database tests run on both SQLite and PostgreSQL 16 (`APEX_TEST_POSTGRES_URL` set).

- `apex.core`: env config, live trading impossible to enable, secret redaction in logs, injectable clock.
- `apex.domain`: Bar, Timeframe, InstrumentSpec, CostModel; 22-instrument default universe (FX majors, US ETFs/stocks, BTC/ETH, ES/MES/NQ/MNQ).
- `apex.db`: 12 tables, Alembic migrations `0001` (schema) and `0002` (pgvector, no-op when unavailable), tested upgrade/downgrade on both engines.
- `apex.marketdata`: provider interface + normalisation; calendars (FX 24x5, CME Globex with daily halt, NYSE RTH with computed holidays, crypto 24x7); validation (NaN, non-positive, OHLC consistency, duplicates/conflicts, misalignment, out-of-session, gaps, spikes) and staleness check; repository with content hashing; ingestion pipeline that records runs and issues.
- `apex.research` (Phase 2): file extraction (`extract.py`: text/markdown, HTML with metadata, PDF text layer + metadata via pypdf, CSV dataset summaries, VTT/SRT transcripts), deterministic extraction of concepts, risk techniques, formulas and if/then trading rules stored as untested hypotheses (`concepts.py`), local embeddings (`embeddings.py`: dependency-free hashing embedder by default, sentence-transformers optional), hybrid BM25 + cosine search, concept and formula lookup, licence note required on import (`library.py`). Migration `0003` adds portable chunk vectors.
- Phase 3 data infrastructure: calendar `session_date` (FX/CME evening sessions roll to the next trading day), approximate CME/FX holiday closures; `resample.py` (calendar-aware resampling with partial-bucket detection); `ResampledProvider` so derived timeframes go through the normal validation + versioning pipeline (source `<src>:rs<tf>`); `reconcile.py` cross-source comparison; `update_bars` incremental, cron-safe updates of completed bars only; `AlpacaStocksProvider` for US equities (mock-tested; needs `APEX_ALPACA_KEY_ID`/`APEX_ALPACA_SECRET_KEY`). `KrakenSpotProvider` (crypto, public endpoint, latest 720 bars only so best for incremental updates; drops the still-forming bar) and `PolygonStocksProvider` (US equities, `APEX_POLYGON_API_KEY`, key never logged; follows `next_url`), both mock-tested. CLI: `update`, `resample`, `reconcile`; `ingest`/`update` accept `--provider alpaca|kraken|polygon`.
- `apex.backtest` (Phase 5 core): bar-based event-driven engine (`engine.py`) that fills at the next bar's open (configurable latency, never same-bar), sizes by equity x leverage rounded to lot size, trades only on target changes, charges commission/spread/slippage/funding from the instrument `CostModel` with a stress multiplier; metrics (`metrics.py`): total return, CAGR, volatility, Sharpe, Sortino, max drawdown, Calmar, win rate, profit factor, expectancy, average win/loss, max consecutive losses, trades/year, exposure, % positive months, costs; reproducible experiments (`experiments.py`) recording data SHA-256, git commit, full params and config, and registering strategy versions with a code hash (refuses to reuse a version number after the strategy code changes). CLI `apex backtest`, `apex strategies`; API `/experiments` (all flagged simulated). Hand-calculated reference tests for fills, P&L, costs, flips, futures multipliers.
- Phase 5 validation (`backtest/validation.py`): rolling or anchored walk-forward optimisation (grid search in-sample, evaluation on the next unseen window, stitched out-of-sample returns, walk-forward efficiency, parameter stability), Probabilistic and Deflated Sharpe Ratio (trial count = grid size x folds), Probability of Backtest Overfitting via CSCV, Monte Carlo bootstrap of outcomes, parameter sensitivity, hold-out split. `run_validation` records a `walk_forward` experiment with all of it; CLI `apex validate`.
- Phase 6 tournament (`backtest/tournament.py`, `strategies/lifecycle.py`): runs walk-forward validation for each strategy x symbol, re-deflates the Sharpe ratio with the family-wide trial count (every walk-forward trial ever recorded for that strategy key), checks promotion gates (min OOS trades 100, family DSR >= 0.95, >= 60% profitable folds, max drawdown <= 25%, PBO <= 0.5), and scores on robustness (DSR, fold consistency, drawdown, PBO, parameter stability; raw return has no weight). Auto-promotion goes experimental -> backtesting -> validation only; `approved` needs a human actor. Every status change writes `strategy_status_changes` and an audit event. `--regime-filter` also enters `<KEY>+RF` variants that share the base strategy's trial family. CLI `apex tournament`, `apex leaderboard`; API `/leaderboard` (flagged simulated).
- Phase 8 regimes (`apex.regime`): causal efficiency-ratio trend regime (`trending`/`range`, matching `StrategyMeta.regimes`), trailing-percentile volatility regime, and a dependency-free Gaussian HMM fitted on a training window then run as a forward filter (never smoothed) on later data. Stability (switch rate, mean run) and an out-of-sample check (forward realised vol per HMM state). `RegimeFiltered` wraps any strategy as `<KEY>+RF` and zeroes positions outside its declared regimes; its version fingerprint covers the wrapped code. CLI `apex regimes`, `--regime-filter` on `backtest`/`validate`. Tests check the HMM recovers known regimes out of sample (>85% accuracy on synthetic switching data) and that every label is causal.
- Phase 7 ML (`apex.ml`, numpy only): causal feature matrix (lagged returns, vol, vol ratio, RSI, efficiency ratio, SMA distance, range/ATR, IBS, volume z), triple-barrier labels recording the last bar each label can depend on, purged + embargoed K-fold splits, L2 logistic regression (IRLS) saved as a JSON model file, and walk-forward out-of-sample probabilities where each model trains only on labels that ended before it is used. Registered strategy ML-LOGIT-001 (hypothesis H53, 24 strategies total). Tests: no leakage (training-set size checked at every retrain), near-chance accuracy on random walks, finds a planted signal. Gradient boosting / ONNX export deferred (would add dependencies).
- Phase 9 slice 1 (reviewed and approved by Jake 2026-11-19): `apex.risk` is an independent package that imports only `apex.core` (enforced by a test). It holds `RiskLimits` (can only be tightened automatically) and `RiskService` (paper mode only; refuses research). Pre-trade checks cover duplicate client order ids, stale data, position size, gross/net exposure, leverage, concurrent positions, consecutive losses, and risk per trade (a stop is required for new risk). Reducing orders are always allowed. A persistent-kill switch trips on drawdown, daily loss or equity <= 0, and only a named human can reset it. `apex.execution` provides the order state machine with deterministic client order ids, `PaperBroker` (idempotent submit; fills at the next bar open using the backtester's cost model) and `Portfolio`. `PaperTrader` runs signal -> risk-capped sizing -> risk check -> paper broker one bar at a time, and flattens when the kill switch engages. Slice 2 (`execution/store.py`, Alembic 0004: `paper_accounts` incl. kill switch, `paper_orders`, `paper_fills`, `paper_positions`) commits each processed bar in one transaction. On restart it rebuilds the trader from the database and reconciles positions, cash and order fill quantities against the fill ledger; any mismatch halts the account until a named human resets it. Client order ids include the account, so replays and parallel accounts never duplicate. CLI `paper-create`, `paper-run` (cron-safe, processes only new stored bars), `paper-reset-kill`; all refuse unless `APEX_TRADING_MODE=paper`. Tests prove a run split by a restart gives identical fills to an uninterrupted run. Correlated-exposure cap: `risk/correlation.py` groups symbols whose absolute return correlation is >= 0.7 (single linkage, min 30 overlapping observations); `RiskService.check` refuses new risk that would put more than `max_cluster_exposure` (40% of equity, tighten-only) into one group, while reducing orders stay allowed. Paper-vs-backtest consistency (`execution/consistency.py`, CLI `paper-compare`, `GET /paper/accounts/{name}/consistency`, shown on the Practice trading tab) re-runs the backtester over exactly the bars an account processed and compares direction per bar, position changes and fill prices; >= 95% direction agreement and <= 1 bp fill gap count as consistent, and known causes (kill switch, losing-streak limit) are explained. Building it exposed two paper bugs, now fixed and tested: a reversal was sent as one order and, if the new side was refused (e.g. risk per trade on the combined size), the old position stayed open; now the close goes first as its own always-allowed reducing order. And every partial trim counted towards the losing streak; now one round trip counts once (open-trade P&L is rebuilt from the fill ledger on restart). Losing streak (Jake's decision 2026-11-19): reaching `max_consecutive_losses` now trips the kill switch, so the account flattens and waits for a named human reset, which also clears the streak (recorded in the audit log). Not done yet: feeding clusters automatically into multi-instrument accounts (current paper accounts hold one symbol, so the cap only bites once those exist), multi-instrument accounts, the 30-day paper record used for `approved`.

## Known limitations

- NYSE early closes treated as full days; CME/FX holidays approximated (25 Dec, 1 Jan, CME Good Friday); other exchange holidays and early closes will show as gap warnings.
- Research search scans all chunks in memory: fine for tens of thousands of chunks; move to PostgreSQL full-text + pgvector beyond that.
- The default embedder is lexical (feature hashing). Install `sentence-transformers` with a local model for true semantic similarity.
- Scanned PDFs (no text layer) are rejected: OCR not supported yet.
- YouTube: APEX imports transcript files the operator obtained through an authorised route; it does not fetch from YouTube. An official-API fetcher (YouTube Data API captions for channels you own, or platform exports) is a later addition.
- No authentication on the API yet: keep it on localhost.
- Backtester does not yet model: margin calls, partial fills, intrabar stop/limit orders, market impact beyond bps slippage, futures roll. Positions open at the end are marked at the last close and counted as a trade (`closed_at_end`).
- Plain `apex backtest` Sharpe is raw; use `apex validate` for out-of-sample, trial-adjusted figures. The tournament uses family-wide trial counts; `apex validate` alone counts only its own grid.
- Session-flat intraday strategies (VWAP-MR, ORB, VWAP-PB, VWAP-BAND, LIQ-PDHL) reset at the first bar of the next session, so with next-bar fills a position can be held from the last bar of a session to the second bar of the next. Exiting before the close needs calendar-aware session-end detection (to do).
- Daily bars use 00:00 UTC of the session date as `ts`; providers with other conventions must be mapped.
