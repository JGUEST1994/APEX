- Meta-labelling (H50): `ml/meta.py` `MetaLabeled` wraps any strategy (`<KEY>+META`; reference strategy ML-META-001 = Donchian breakout + meta-model). At each new primary trade a walk-forward logistic model (causal features + side, trained only on earlier events whose triple-barrier label had finished) estimates P(the trade reaches its profit barrier first); the trade is skipped below `meta_threshold`. It can only remove trades, never add or flip them. Before enough labelled events exist it follows the primary (or skips, configurable). Tests: causality, filter-only, learns to drop the losing side of a no-skill primary in a drifting market and raises its Sharpe, warm-up modes.
- Multi-instrument strategies: `strategies/multi.py` (`MultiStrategy` returns a signed weight per leg; separate registry so single-asset tests are unaffected) and `backtest/portfolio.py` (`run_portfolio_backtest`: legs aligned on common timestamps, next-open fills, same cost and funding model, a trade is one round trip of the book, closed on flat or reversal). A one-leg portfolio reproduces the single-instrument engine exactly (equity, costs and per-trade P&L). CLI `backtest-pair` records an experiment like any backtest; `/strategies` and `apex strategies` list it. Tests: causality, always hedged, Sharpe > 1.5 on planted cointegrated pairs vs < 1 on unrelated random walks, fills at next open. Walk-forward, PBO, sensitivity, `apex validate --symbol ETHUSDT/BTCUSDT` and the tournament (`--symbols SPY,ETHUSDT/BTCUSDT`; pairs go only to multi-instrument strategies and are never regime-wrapped) now accept them; the leaderboard shows the pair with its common asset class (or `mixed`). Second multi strategy TF-XASSET-001 (H05 cross-asset trend portfolio): any number of legs (`legs = None`), each market long/short by the sign of its trailing return, inverse-volatility weights scaled to gross, rebalanced every 21 bars and held in between, optional long-only. `apex backtest-pair --strategy TF-XASSET-001 --symbols SPY,BTCUSDT,ETHUSDT` and `--symbol A/B/C` in validate/tournament work. - `apex.backtest` (Phase 5 core): bar-based event-driven engine (`engine.py`) that fills at the next bar's open (configurable latency, never same-bar), sizes by equity x leverage rounded to lot size, trades only on target changes, charges commission/spread/slippage/funding from the instrument `CostModel` with a stress multiplier; metrics (`metrics.py`): total return, CAGR, volatility, Sharpe, Sortino, max drawdown, Calmar, win rate, profit factor, expectancy, average win/loss, max consecutive losses, trades/year, exposure, % positive months, costs; reproducible experiments (`experiments.py`) recording data SHA-256, git commit, full params and config, and registering strategy versions with a code hash (refuses to reuse a version number after the strategy code changes). - Phase 5 validation (`backtest/validation.py`): rolling or anchored walk-forward optimisation (grid search in-sample, evaluation on the next unseen window, stitched out-of-sample returns, walk-forward efficiency, parameter stability), Probabilistic and Deflated Sharpe Ratio (trial count = grid size x folds; each trial is judged over as many out-of-sample returns as the result, i.e. zero-skill Sharpe variance 1/(T-1)), Probability of Backtest Overfitting via CSCV, Monte Carlo bootstrap of outcomes, parameter sensitivity, hold-out split. `run_validation` records a `walk_forward` experiment with all of it; CLI `apex validate`.
- Phase 6 tournament (`backtest/tournament.py`, `strategies/lifecycle.py`): runs walk-forward validation for each strategy x symbol, re-deflates the Sharpe ratio with the family-wide trial count (every walk-forward trial ever recorded for that strategy key), checks promotion gates (min OOS trades 100, family DSR >= 0.95, >= 60% profitable folds, max drawdown <= 25%, PBO <= 0.5), and scores on robustness (DSR, fold consistency, drawdown, PBO, parameter stability; raw return has no weight). Gate failures are explained in plain English with the technical name in brackets (e.g. "could be luck: confidence the edge is real 41%, needs 95% (deflated Sharpe)"); thresholds unchanged. Auto-promotion goes experimental -> backtesting -> validation only; `approved` needs a human actor. Every status change writes `strategy_status_changes` and an audit event. `--regime-filter` also enters `<KEY>+RF` variants that share the base strategy's trial family. CLI `apex tournament`, `apex leaderboard`; API `/leaderboard` (flagged simulated).
- Phase 8 regimes (`apex.regime`): causal efficiency-ratio trend regime (`trending`/`range`, matching `StrategyMeta.regimes`), trailing-percentile volatility regime, and a dependency-free Gaussian HMM fitted on a training window then run as a forward filter (never smoothed) on later data. Stability (switch rate, mean run) and an out-of-sample check (forward realised vol per HMM state). `RegimeFiltered` wraps any strategy as `<KEY>+RF` and zeroes positions outside its declared regimes; its version fingerprint covers the wrapped code. CLI `apex regimes`, `--regime-filter` on `backtest`/`validate`. Tests check the HMM recovers known regimes out of sample (>85% accuracy on synthetic switching data) and that every label is causal.

- Phase 9 slice 1 (reviewed and approved by Jake 2026-11-19): `apex.risk` is an independent package that imports only `apex.core` (enforced by a test). It holds `RiskLimits` (can only be tightened automatically) and `RiskService` (paper mode only; refuses research). Pre-trade checks cover duplicate client order ids, stale data, position size, gross/net exposure, leverage, concurrent positions, consecutive losses, and risk per trade (a stop is required for new risk). Reducing orders are always allowed. A persistent-kill switch trips on drawdown, daily loss or equity <= 0, and only a named human can reset it. `apex.execution` provides the order state machine with deterministic client order ids, `PaperBroker` (idempotent submit; fills at the next bar open using the backtester's cost model) and `Portfolio`. `PaperTrader` runs signal -> risk-capped sizing -> risk check -> paper broker one bar at a time, and flattens when the kill switch engages. Slice 2 (`execution/store.py`, Alembic 0004: `paper_accounts` incl. kill switch, `paper_orders`, `paper_fills`, `paper_positions`) commits each processed bar in one transaction. On restart it rebuilds the trader from the database and reconciles positions, cash and order fill quantities against the fill ledger; any mismatch halts the account until a named human resets it. Client order ids include the account, so replays and parallel accounts never duplicate. CLI `paper-create`, `paper-run` (cron-safe, processes only new stored bars), `paper-reset-kill`; all refuse unless `APEX_TRADING_MODE=paper`. Tests prove a run split by a restart gives identical fills to an uninterrupted run. Correlated-exposure cap: `risk/correlation.py` groups symbols whose absolute return correlation is >= 0.7 (single linkage, min 30 overlapping observations); `RiskService.check` refuses new risk that would put more than `max_cluster_exposure` (40% of equity, tighten-only) into one group, while reducing orders stay allowed. Paper-vs-backtest consistency (`execution/consistency.py`, CLI `paper-compare`, `GET /paper/accounts/{name}/consistency`, shown on the Practice trading tab) re-runs the backtester over exactly the bars an account processed and compares direction per bar, position changes and fill prices; >= 95% direction agreement and <= 1 bp fill gap count as consistent, and known causes (kill switch, losing-streak limit) are explained. Building it exposed two paper bugs, now fixed and tested: a reversal was sent as one order and, if the new side was refused (e.g. risk per trade on the combined size), the old position stayed open; now the close goes first as its own always-allowed reducing order. And every partial trim counted towards the losing streak; now one round trip counts once (open-trade P&L is rebuilt from the fill ledger on restart). Losing streak (Jake's decision 2026-11-19): reaching `max_consecutive_losses` now trips the kill switch, so the account flattens and waits for a named human reset, which also clears the streak (recorded in the audit log). Multi-instrument paper accounts (Alembic 0005 adds `paper_accounts.symbols`): one strategy runs on several instruments with shared cash, one risk service and one kill switch; each instrument gets its own signal; bars are processed per timestamp (closed markets are simply absent, so crypto trades at weekends and stocks do not); correlated groups for the exposure cap come from the last 120 bars of returns; later instruments in the same bar are checked as if earlier approved orders had filled. Restart, reconciliation and the consistency report (now per symbol) cover several instruments. CLI: `paper-create --symbol SPY,QQQ,BTCUSDT`. Multi-instrument strategies in paper (pairs, ETF vs basket, cross-asset trend, cross-sectional momentum): `paper-create --strategy STAT-PAIR-001 --symbol QQQ,SPY` (legs in the order given, leg count checked); the trader feeds the aligned leg histories to `target_weights`, trades only at timestamps where every leg has a bar, turns each leg's weight into units with the same notional and risk-per-trade caps as single strategies, sends every leg through the same risk checks and kill switch, and skips drift smaller than 10% of a leg (stateless, so restarts give identical fills). The paper-vs-backtest report covers them: the whole book is re-run once through the portfolio backtester on the legs' common bars and each leg's direction, position changes and fill prices are compared with its paper fills (a TF-XASSET-001 and a STAT-PAIR-001 account agree 100% with 0 bp fill gap in tests). Practice record (`paper_record.py`, CLI `paper-record`, `GET /paper/accounts/{name}/record`, shown on the Practice trading tab): read-only roadmap gate "30 days continuous paper running with no unhandled errors"; counts only bars dated after the account was created, and needs the account still running (not halted, kill switch off, newest bar <= 4 days old), no kill-switch/halt audit events since creation, and a consistent paper-vs-backtest report. It never changes a strategy's status. Approval (Jake's decision 2026-11-20, `approval.py`, CLI `strategy-approve --account X --by NAME [--reason]`): a named person only (not system/risk/scheduler), only when that account's record is READY, only for a strategy version already at `validation` (tournament gate) or `paper_trading`, and only if its code is unchanged since the version was registered; records `validation -> paper_trading` (system, with the record as evidence) then `paper_trading -> approved` (the person) in the status history and audit log. No API route can approve. Approval enables no real-money trading.

- Faster walk-forward (2026-11-20): each strategy's signal is worked out once over the whole history (`validation._signal`) and each unseen window is backtested on its slice (`_window`), instead of replaying all earlier history before every window. Valid because every strategy is causal (look-ahead tests cover every single-market strategy and, new, every multi-market one); a new test checks the unseen-window returns are identical to the old replay. Out-of-sample returns, trades and every gate figure are unchanged; 1.4-7x faster on the cases measured (ML strategies gain most). Per-window Sharpe (`mean_oos_sharpe`, the leaderboard's `oos_sharpe`, walk-forward efficiency) is now measured on the unseen window alone; before, it was diluted by the flat warm-up bars.
- Luck test fixed for long histories (2026-11-20): the deflated Sharpe's benchmark used the spread of the training-window Sharpes (2 years of daily bars, a few weeks of 5-minute bars), which are far noisier than a Sharpe over the whole stitched out-of-sample series. So the training length set the bar, and because every fold also counts as a try, more history raised it: on synthetic data with a real built-in edge (MR-IBS-001, judged as if tried on 7 markets) confidence fell from 95.5% with 6 years to 0.4% with 26. Now each try is judged over the same number of out-of-sample returns (`validation.null_sharpe_variance`, 1/(T-1)), and the tournament re-judges every recorded result that way (stored `sr_variance` is ignored). The try count is unchanged (every setting on every fold, summed over the family), so the bar stays conservative: the same edge now reads 96.4%, 98.2% and 100% with 6, 12 and 26 years, and a no-edge random walk 24.5%, 2.1% and 0.9%. Dashboard and user guide wording updated.

## Known limitations

- NYSE regular early closes (13:00 ET on 3 July and 24 December when Mon-Thu, and the day after Thanksgiving) are modelled, and so are one-off full closures since 2000 (`NYSE_SPECIAL_CLOSURES`: 9/11, Hurricane Sandy, presidential days of mourning up to Carter 2025-01-09); future one-offs must be added by hand. CME/FX holidays approximated (25 Dec, 1 Jan, CME Good Friday); other exchange holidays and early closes will show as gap warnings.
- Research search scans chunks in memory up to 20,000 chunks. Beyond that, on PostgreSQL, a GIN full-text index (migration 0006) picks the best 2,000 keyword candidates first and only those are re-scored, so a chunk with no keyword match is not found and BM25 statistics come from the candidates. SQLite always scans in memory. pgvector-based semantic candidates are not used yet.
- The default embedder is lexical (feature hashing). Install `sentence-transformers` with a local model for true semantic similarity.
- Scanned PDFs (no text layer) are rejected: OCR not supported yet.
- YouTube: APEX imports transcript files the operator obtained through an authorised route; it does not fetch from YouTube. An official-API fetcher (YouTube Data API captions for channels you own, or platform exports) is a later addition.
- API access control is one optional shared token (`APEX_API_TOKEN`; no user accounts). Without it, keep the API on localhost (the default, including Docker).
- Backtester does not yet model: margin calls, partial fills, intrabar stop/limit orders, market impact beyond bps slippage, or roll costs (use a back-adjusted `csv-cont` series for futures; the roll itself is not charged). Positions open at the end are marked at the last close and counted as a trade (`closed_at_end`).
- Plain `apex backtest` Sharpe is raw; use `apex validate` for out-of-sample, trial-adjusted figures. The tournament uses family-wide trial counts; `apex validate` alone counts only its own grid.
- Session-close detection uses the calendars above, so intraday strategies inherit their approximations (CME/FX early closes are not known, and future one-off NYSE closures must be added by hand).
- Daily bars use 00:00 UTC of the session date as `ts`; providers with other conventions must be mapped.
- Forex has no currency conversion: the backtester sizes `leverage x equity / price` units and counts profit in the pair's quote currency as if it were the account's. So USDJPY (about 150 yen a dollar) rounds down to zero 1,000-unit lots and never trades (21 empty results in the 2026-11-20 research run), and USDCAD is valued in Canadian dollars. A fix also changes practice (paper) sizing, so it waits for Jake.
- VWAP-EARN-001 is tested in the research run only when `APEX_SEC_USER_AGENT` (the operator's own name and email, as the SEC asks) is set as a repository secret; without it the run leaves the idea out and says why.
- Free data history: Alpaca's free (IEX) feed reaches back only to about 2020, so daily stock research uses Tiingo. `apex tournament` runs each strategy with its default settings only (no grid), so nothing is tuned and PBO is not computed there; walk-forward training windows are each backtested on their own, so their cost still grows with the number of windows times the training length.
